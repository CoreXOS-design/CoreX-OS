## Audit fixes 2026-10-19 - lease side (A1, A5, A7, A12, A16, A24, A26; source: `/root/rental-e2e-2026-10-19.md` section 2A; tests `LeaseAuditFixesTest`, and two in `RentalInspectionMoveOutComparisonTest`)

What was chosen, in one place (code wins where this file and an older section disagree):

- **A1 - a "Create lease only" draft is not a dead end (amends §15.4 / §15.6, which described the two buttons on the capture screen only).** On a draft lease with no agreement in flight (never prepared, or the last one was declined / cancelled / expired) the Lease Hub shows a **"Get this lease signed"** card (`resources/views/corex/leases/_draft-follow-up.blade.php`, anchor `#draft-follow-up`; the Next bar says "Get the lease signed"). Three ways forward, in this order: (1) **Prepare the agreement for signing** - `POST corex/leases/{lease}/signing/prepare` -> `LeaseCaptureService::prepareDraftForSigning()`: the SAME gate, guard and flow as the capture screen's second button (`LeaseSigningLauncher::launch`), with the agreement details typed on the card saved first; required details or signer gaps are listed and nothing is created; pressing it twice returns the same agreement; the agent lands on Fill & review, nothing is sent. (2) **Attach the signed paper copy** - `POST corex/leases/{lease}/signing/signed-copy` -> `attachSignedCopyToDraft()`: files the copy exactly as at capture, activates the lease (the one-active-lease rule applies; a refusal rolls everything back and removes the file), marks it `signed_on_paper`, gives the parties portal access and their copy by email (same best-effort rule as at capture). (3) **Activate without a signed agreement** - the existing `activate` action, now a labelled, confirmed choice; every such activation writes a lease event `activated_without_agreement` naming who. Permission `leases.create`; lease scope `guardRentalRecordScope`; a renewal draft keeps its own screens (the card is not offered). New lease events: `signed_copy_attached_later`, `activated_without_agreement`.
- **A5 - an accepted notice ends the tenancy on its date (amends `rental-renewals.md` §22 rule 2).** New agency setting `lease_settings.end_tenancy_on_move_out_date` (`LeaseSetting::endTenancyOnMoveOutDateFor`, **default ON**; settings page + Setup Wizard `leases` step; has()-guarded saver; audited in `rental_setting_audit`). On: a lease with an accepted notice (notice date AND move-out date) expires on the move-out date by the daily `leases:advance-terms` even when no out-inspection was ever completed; the event says so. A lease that is merely past its plain end date with no notice is NOT ended by this (that is the record-an-outcome / month-to-month path). Off: the old rule - only a completed out-inspection (with `auto_restore_status_on_lease_ended` on) ends it. The property goes back to its pre-let status only when `auto_restore_status_on_lease_ended` is on, exactly as before (portal-silent, agent told). Existing leases with a notice whose move-out date has already passed WILL be ended by the next nightly run on an agency with the default.
- **A7 - no lease against a non-approved application (enforces §15.25).** The capture request, the capture writer (`LeaseCaptureService::capture`, so the API and any future caller too) and the capture screen all refuse an application whose status is not `approved`, with one sentence (`LeaseCaptureService::applicationNotApprovedMessage`). The screen redirects back to the application. Renewals and take-on pass no application and are unaffected.
- **A12 - lease edit.** `LeaseController::update` keeps `is_month_to_month` when the field is not posted (the web form now posts a hidden 0 so un-ticking works) and applies the same "month-to-month XOR end date" rule as capture, through the one shared `LeaseCaptureService::monthToMonthConflict()`; it is checked only when the edit touches either field.
- **A16 - the partner on the application is not typed twice.** The capture screen seeds the application's partner / co-applicant (`spouse_name` / `spouse_id`) as a second tenant when they are already a contact of the agency **matched on ID number** (never on name alone - same principle as `TenantContactResolver`). When they are not a contact, the screen offers **"Add as a tenant"**: `POST corex/leases/application-co-applicant` creates the contact (name + ID from the application, agency/branch of the application; reused if already there, never duplicated; written to the application's audit trail) and adds them to the picker. The agent can remove either row. No contact is ever created by merely opening the screen.
- **A24 - the deposit comparison records an amount, nothing more (Johan: money stays with reOS).** `rental_inspection_item_findings.amount` (nullable, rand); optional on the finding form, validated 0 - 99,999,999.99, shown with the finding, recorded in the inspection's history (`finding_recorded` / `finding_superseded` now carry the figures). No deduction, ledger, invoice or payout; `charge_tenant` still feeds nothing.
- **A26 - no literal let status.** `PropertyStatusFollowsLeaseService::leasedOutStatusFor($agencyId)` is the only place a "let" status is named (first of `let_out`, `rented` that the agency's status vocabulary accepts); `LeaseActivationService` and the notice-reversal paths go through it. If the vocabulary accepts none, the property is left alone but NOT silently: a lease event `property_status_not_updated`, a log line, a warning on the lease screen while the lease is active, and the same sentence in the "Lease activated" message. (Today `let_out` is a system status valid for every agency, so this guards the future rather than fixing a live case.)
- **Not done here (other clusters / by ruling):** FICA stays not-prefilled (A15) and money stays with reOS (A24) - both Johan's rulings; the schema snapshot (`database/schema/mysql-schema.sql`) was NOT re-dumped by this work (two new migrations: `2026_11_19_200000_*`, `2026_11_19_200100_*`) - dump once, after all clusters' migrations are in.
