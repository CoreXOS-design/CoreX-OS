# MIC Work tab — spec v1 (approved by Johan 31 Oct 2026)

## The goal
An agent opens MIC on their first day and one screen tells them which properties to chase today and why. Every P24 and PP advert is matched into one property record, and the list is ordered so the top rows are the ones we know most about and that are most likely to become a mandate.
- One screen: the Work tab is where the agent works. The other MIC tabs stay for now; nothing in this spec needs them.
- One row per PROPERTY (tracked property file), not per advert. Both portals, our own stock, P24 alert emails, deeds and CMA data on the same line.
- Tiles on top, not a greeting: "Hi Johan, here's your week" is removed. Hot-pocket tiles replace it; one click filters the list to that pocket.
- Ordered by opportunity score, not last seen (section 4).
- Agency walls: public portal facts are shared between agencies; claims, notes, contacts, deeds, CMA reports stay with the agency that made them.
- Numbers say how sure they are. Days on market = portal listed date when known; else first-seen date, shown "~45 days" (accurate to 7 days when the suburb had a complete crawl in the 7 days before first seen); if the advert was already there on our first read of the suburb (or after a crawl gap > 7 days) shown as a minimum "45+ days".

## 1. Tiles (11) across the top
Each tile: a count + one-line reason; click = filter the list to that pocket (or open its panel). One row of tiles fits the screen (no scrolling). Agency picks which tiles show (Settings); default all 11. A tile with too little data says so ("3 sales — too few to rank"), never invents.
1 Stuck on the market — long DOM, price cuts, re-listed (dead advert + new advert on same property). Data: 1,566 active adverts with a cut (847 last 30 d, 127 cut 2+); 659 re-list pairs; 2,456 P24 alert cuts. DOM per rule above.
2 Owner selling privately — advertiser_type = owner (P24 listed_by_owner tile image; PP "LISTED PRIVATELY"). Not captured yet.
3 Under offer, sold or gone — P24 ribbon already captured (1,048 under offer, 251 sold, 351 turned in last 30 d); PP "Under Offer" banner not sent yet; "Gone" = missing from a complete suburb crawl (section 6).
4 Where our stock sits — own properties by suburb/type/price band (165 on market, 518 sold, 2,564 withdrawn, 991 expired). Needs suburb ids.
5 What sells fastest for us + lookalikes — own sales listed→sold days (74 real-dated sales, avg ~30 d) by pocket (suburb+type+beds+price band); lookalike market adverts (37 pockets → ≥1,938 adverts). Show "based on N sales".
6 Where our leads come from — portal_leads (922, 900 linked) + property_portal_metrics (41,204 daily rows): leads per listing / per listing-week by pocket.
7 Buyers waiting, stock short — active sale wishlists (369) vs own stock vs market stock per pocket (31 pockets with 3+ buyers).
8 New from P24 alerts — alert adverts this week + alert price drops (14,092 alert rows, 63% matched to a MIC advert). Envelope icon.
9 Market prices here — avg sold vs asking, sales per year, stock trend per suburb: CMA comps (1,726 sales last 24 m), deeds, P24 suburb trends pages.
10 Neighbours of a sale (Elize's canvass rule) — trigger = deeds registration, our own sale, CMA sale, or a portal advert turning Under Offer/Sold. Neighbours = same street, numbers within 5 on the same side (same odd/even) + nearest numbers on the opposite side; sectional = other units in the same complex/scheme (or same complex land size in the suburb). Live from day one; drops off after 6 months (setting). Click the tile → panel of trigger properties, newest first, time filter (this month, 1,2,3,4,5,6 months), trigger-type filter (registered, sold, under offer, our sale), suburb filter. Click a trigger → the homes around it: address, deeds owner if held, on market?, our last contact; actions: claim, call, marketing drop to the block.
11 Market data last refreshed — oldest full refresh across the agency's suburbs ("Margate: P24 12 days ago"), red past the refresh interval (default 7 days). Click → every suburb the agency works, last full P24 read + last full PP read, oldest first, "Open in P24" / "Open in PP" buttons. Agents see their suburbs first; managers see all.

## 2. The property record (Excel-style row, expand in place, no cards)
Columns: Sources (icons: P24, PP, envelope = P24 alert, our stock, deeds, CMA comps, Owner) · Address (one address rule shared with filter + search; no address → "Suburb · type · complex N m²") · Property (type, beds, baths, garages, floor m², erf m², best value across adverts) · Price (asking + move since first seen "▼ R150k, 2 cuts") · Against the market (asking vs suburb avg sold for type/beds; R/m² vs suburb) · Who's selling (agency count + names, or Owner) · Time (DOM per rule; last seen) · Flags (Under offer, Reduced, Re-listed, Gone, Exclusive to PP) · Buyers (strong/mid) · Our work (claimed by, status, not-on-market reason, last contact — own agency only) · Next action (one button: Claim / Call owner / Pitch / Investigate).
Expand in place: adverts (portal, agency, agent, price, listed date, link) · P24 alerts (date, price, envelope) · price history · deeds (owner, years owned, last sale price/date, bond) · recent sales nearby (CMA) · matched buyers · our history (claims, contacts, notes, not-on-market reasons; kept when the property comes back on market).
Finding: one search box (must also match the file's resolved address — today "Newport" misses PP-T4203603), sortable columns, a filter per tile.

## 3. Opportunity score
Score per property; each row shows its top 2 reasons as chips. Default weights (agency settings): Seller signals 30% (cuts, re-listed, long DOM incl. first-seen estimate, owner advertising, mandate ended elsewhere) · Buyer demand 25% (strong/mid matches, buyers-waiting pocket) · Pocket heat 20% (fast-selling pocket, lead pocket, under-offer/sold activity in same suburb+type+band) · What we know 15% (address, deeds owner, alert history, several adverts agreeing, full facts) · Reachable 10% (owner contact from deeds/advert, nobody in our agency working it, no opt-out).
Rules: claimed by a colleague → down for others with the colleague's name; marked not on market → down until cleared or back on market, then up with "Back on the market" chip + old history; do-not-contact/opted out → no call action. Other sorts one click away: price, newest, biggest cut, most buyers.

### 11.1 cc5 contracts (written 31 Oct 2026, BEFORE build; cc6 codes the screen against these; change only by editing this section in a commit)

**Namespaces / files (all new, cc5 owns):** `app/Services/MarketIntelligence/Pockets/*`, `app/Services/MarketIntelligence/Score/*`, `app/Services/MarketIntelligence/Dom/*`, `app/Models/MicFileStat.php`, `app/Models/MicPocketStat.php`, `app/Models/MicAgencySetting.php`.

**Shared keys.** `suburb_id` = `p24_suburbs.id` (the existing P24 suburb table; 5.1). `type_key` = canonical property type slug from table `property_type_map` (5.2): `house, apartment, townhouse, land, farm, commercial, industrial, other`. `band` = price band slug `lt1m, 1to2m, 2to3m, 3to5m, gte5m` (edges are agency settings, defaults 1m/2m/3m/5m). `beds` = integer, 0 = none/land, capped at 5 (5 = "5+").

**Settings (storage = `mic_agency_settings`, one row per agency, JSON-cast columns; cc6 builds the Settings page, cc5 owns the model).** `MicAgencySetting::for(int $agencyId): MicAgencySetting` (creates defaults in memory, never writes on read). Getters: `scoreWeights(): array{seller:int,buyer:int,pocket:int,known:int,reachable:int}` default 30/25/20/15/10 (must sum to 100, else defaults used + logged); `tilesShown(): int[]` default 1..11; `priceBandEdges(): int[]` default [1000000,2000000,3000000,5000000]; `domApproxWindowDays(): int` default 7; `fastSaleDays(): int` default 45; `staleActiveDays(): int` default 14; `minSalesForPocket(): int` default 3.
**Rule accessors for cc4 (added 31 Oct 17:20, AT-519 5.11) — read as `MicAgencySetting::for($agencyId)->…()`; no value is hard-coded elsewhere:** `refreshStaleDays(): int` = days after which a suburb's market data is stale = **the SAME value the Settings page saves as "Market data refresh – Every N days" (`refresh_interval_days`, default 7); an alias, not a second setting** · `approxReadMinSharePct(): int` = share (%) of a suburb's live adverts a crawl must have seen to count as an approx read (default **50**, capped 1–100) · `approxReadMinAdverts(): int` = and at least this many adverts (default **3**) · `workingSuburbMinCount(): int` = with no Areas ticked, a suburb counts as "ours" when it has at least this many of our stock, claims or leads in the last 12 months (default **3**; Settings page → Areas: "Count a suburb as ours from N listings/claims/leads", stored as `working_suburb_min_count`). **Tile result (every tile service returns this).** `App\Services\MarketIntelligence\Pockets\TileResult` (final, readonly): `int $tile` (spec tile number) · `string $key` · `?int $count` · `string $reason` (one line, plain English, already includes "based on N" where relevant) · `array $filter` (query params the Work list applies, exactly `['tile' => '<key>']` plus optional extra params) · `bool $tooLittleData` · `?string $tooLittleMessage` (shown instead of the count when true, e.g. "3 sales — too few to rank") · `array $meta` (tile-specific numbers, see below). `toArray()` returns the same keys.

### 13.15 Buyer match rules - one set for MIC and Core Matches (Johan, 2 Nov 2026 04:34: "my buyer wants x but mic shows everything else")

**Why.** Before this, MIC (adverts) and Core Matches (own stock) judged a buyer's wishlist by different rules: price tolerance 10% on MIC and 30% on Core Matches; the property type only a family gate (a House-only buyer saw Townhouses at "83% strong", because a wrong type cost 5 of 30 points); beds-max, parking and auction ignored; an advert with nothing captured scored as if it fitted. A buyer's matches now mean the same on every screen.

**Where it lives.** `App\Services\Matching\BuyerMatchRules` (the hard filters) and `MatchingService::assess()` (the verdict: score, tier, unverified list; `score()` is `assess()['score']`). Core Matches (`propertiesForMatch`, `propertyCountsForMatches`), the MIC cache (`PropertyMatchScoringService::canonicalBestAcross` -> `prospecting_buyer_matches`), the property page and the buyer portal all call that one method. The MIC banner count, the "Buyers N strong · N mid" line on each card (`mic_file_stats`) and the Buyers waiting tile all read the same cache, so they cannot disagree.

**Hard filters - an advert or property that fails any ONE is not a match and is not shown (score 0):**
1. Listing type (sale vs rental).
2. Price: at or above the wishlist minimum (never relaxed) and at most `max x (1 + tolerance)`. The tolerance is the agency setting **"Price tolerance above a buyer's maximum (%)"**, `mic_agency_settings.values.price_tolerance_pct`, default 10, 0-50, on the MIC Settings page (Adverts view box); `MicAgencySetting::priceTolerancePct()`. Inside the tolerance the price component decays linearly (at the maximum 100%, at the edge 0%).
3. Category when set (an advert with no category takes it from its type: house / apartment / townhouse = Residential, commercial / industrial = Commercial).
4. Property type in the wishlist's types when set, compared by the MIC canonical type (`PropertyTypeResolver`: "Apartment" = "Apartment / Flat" = "Flat"; Duplex / Simplex = Townhouse; **a Townhouse is not a House**). A type the map cannot read falls back to the family (built / land / farm / commercial): another family excludes, the same family is kept as unverified.
5. Suburbs when set (an open wishlist matches anywhere).
6. Bedrooms at least the minimum and at most the maximum; baths, garages, parking at least the minimum; floor and erf size within their min / max - each only when set.
7. Deal-breaker features present, or a must-have missing - excluded.
8. Auction lots (status `on_auction`) excluded when the buyer is not open to auctions (`open_to_auction = false`; empty = open).

**Unknown values.** An advert that has not captured a value the buyer asked about (beds, baths, garages, parking, sizes, price, type, category, listing type, or any features when the wishlist has deal-breakers / must-haves / nice-to-haves) is NOT excluded on that field. The field is listed as **unverified** (stored in `prospecting_buyer_matches.matched_features.unverified`), is left out of the score, and a match with anything unverified tops out at 79 - it cannot be "strong". A sale price under R10,000 counts as "no price" (a typo or placeholder), not a bargain.

**Score (only among those that pass).** Only what the buyer stated counts: price distance to their maximum 25, suburb 20, beds 8, baths 7, garages 5, category 5, type 5, sizes 5 each, nice-to-haves 15 (share present), must-haves 15. A wishlist that states little therefore gives 100% to everything that fits it - that is correct and is the answer to "why are all 55 100%": the wishlist said little. **Tiers** are the engine's: strong 80+ and mid 50-79 (`buyer_match_tiers`, agency-configurable; Core Matches: strong 80 / good 65 / fair 50). The MIC %-slider, the buyer-banner count and the headline counts default to the **strong** line (`buyer_match_tiers.strong_min_score`, 80; Johan 2 Nov 05:21: "shows everything else"); the slider stays so an agent can widen to mid (50) when strong is thin (`mic_match_threshold` is no longer read by MIC). The card's "Buyers N strong · N mid" line still shows both tiers.

**Not built here (Johan's call, spec 5.1).** Role Manager entry and Setup Wizard entry for the new tolerance setting. The wizard's MIC step does not carry the other MIC settings today either; it stays only on the MIC Settings page until Johan decides.

**Case that started it.** Alex Swanepoel (contact 18742), wishlist 702: sale, up to R1,000,000, Residential, types **House + Apartment / Flat + Townhouse** (the line "For sale · up to R 1,000,000 · Residential · House" shows only the first type), no suburbs / beds / features. Under the rules a Townhouse at R950,000 IS a match for him (it is on his list). The same wishlist ticked House only would not match it - the tests cover both.

**Tests.** `tests/Feature/Matching/BuyerMatchRulesTest.php`: Alex's wishlist against a House, a Townhouse, a flat, land, a House at R1.05m (inside 10%, decayed, not strong), a House at R1.2m (out), the minimum never relaxed, the tolerance as a setting (0 and 25), deal-breaker present / features unknown, unknown type, beds / baths / garages / erf / bedrooms-max / auction, listing type and category, and **Core Matches and the MIC cache agreeing, case by case, on both the verdict and the score**. Three older tests that encoded the superseded rules were updated (Townhouse for an apartment buyer, the 30% near-miss, the 75 line).

The manual "Import as Other Agency Stock" flow (`getPropertyDetail` -> `/api/v1/other-agency-stock/import`) is a different path (it creates agency stock) and is NOT reused. A CoreX page could not talk to the extension at all (no `externally_connectable`, no content script on a CoreX domain).

**How the click works.**
1. `_advert-fetch.blade.php` (one `@include` on the agent / reference line of the card) shows the label and the button. The page script `public/js/mic-advert-fetch.js` (loaded once from `work.blade.php`, so it survives the tick refresh) handles every click by event delegation.
2. **Bridge, no extension id:** extension 3.16.0 adds `content-corex-bridge.js` on `https://corexos.co.za/*` and `https://*.corexos.co.za/*`. The page and the bridge talk by `window.postMessage` (`source: 'corex-page'` / `'corex-ext'`, same window, same origin only). The bridge relays `read-advert` to the background worker (`micReadAdvert`).
3. **Background (`background.js runReadAdvert`):** guards (the page's origin must be the CoreX site the extension is signed in to; the advert must be an https URL on `www.property24.com` / `www.privateproperty.co.za`; the extension must hold its API token) -> a BACKGROUND tab (`active: false`) on the advert -> waits for the load (25 s) -> `getListingFacts` (PP: server variables first) -> `POST /api/prospecting/import` with `search_context.detail_only = true` -> closes the tab -> answers the page (`ok` or a reason). One read at a time per browser (a promise chain) with at least 4 s between pages. A page that does not parse is never posted; the advert stays unread.
4. **Page:** shows a wheel "Reading P24..."; on `ok` it fetches the current list fragment (`?_fragments=1`, the endpoint the tick refresh already uses) and swaps THIS card's row in place, so the description, facts, photos, features, agent and label come from the server, not from the script. 30 s without an answer -> "Couldn't read - open advert". No extension, or an extension older than 3.16 (no `pong` within 0.7 s): the advert opens in a new tab and a one-line note says "Install the CoreX Chrome extension for one-click details" with a link to My Portal -> Tools -> Chrome extension. The extension signed out / another site -> a note that says so.
5. **Server:** the existing ingest, plus: the `detail_only` read needs the `access_prospecting` right (the same right that lets an agent claim; 403 otherwise); it stores who read it (`prospecting_listings.details_read_by`) and the card wording fingerprint (`details_read_card_hash`); it writes ONE line on the file's history (`tracked_property_agency_work_events.kind = 'details_read'`, "Full details read from P24" with the user and time, shown in the Work record's History). Agency scope is unchanged: the advert is looked up by agency + portal + ref, so another agency's advert is "unknown" and nothing is written. A lone advert with no property file has no history to write to (the label still shows who and when).
6. **Not done on purpose:** the photo fingerprint of the old 3.15.1 detail step (cross-portal photo matching) is not restored; contact numbers are never read (11.2).
**Decision recorded (design call, not Johan's):** the row refresh reuses the existing list fragment instead of a new row endpoint. It builds the row with exactly the code the page uses (no second copy of the card's ~15 inputs to drift), at the cost of one page-sized fragment per read (a read takes seconds anyway). If it is slow on a big page, add a `_row=<id>` narrowing to the same fragment.

### 13.18 Buyer wants vs property has - data contract (Johan, 2 Nov 05:30; view by cc6)

`MicWorkList::forFiles($keys, $agencyId, $buyerId)` adds `buyer_fit` to each file record when a buyer is selected (null otherwise). It comes from `MatchingService::fit()`, which runs `BuyerMatchRules::evaluate()` to the end - the very pass the hard filters and the unverified list use (`check()` is the same pass stopped at the first miss), and the score from the same pass. Nothing is calculated twice. The panel shows the buyer's **best** active wishlist for that file (the one that made the score).

```
buyer_fit: { first_name, wishlist_id, score (0 = a hard miss, not a match), tier (strong|good|fair|null), unverified: [labels],
  fields: [ { key, label, wants, has, state } ],   // order: price, type, suburb, beds, baths, garages, parking, erf, floor
  must_haves:    [ { label, state } ],
  deal_breakers: [ { label, state } ] }
state: ok | miss | unknown (the advert has no value) | na (the wishlist does not state it)
```
`wants` / `has` are display strings: price "≤ R1.0m", "R800k – R1.0m", "≥ R800k" / "R950k"; type "House · Townhouse" / the advert's type; suburb the wishlist's names / the advert's suburb; beds, baths, garages, parking "3+", "2–4", "≤ 4" / "2"; erf, floor "500+ m²", "500–800 m²" / "650 m²". `has` is "" when the advert has no value; `wants` is "" when the state is `na`. For a must-have `miss` = the advert's features are known and it lacks it; deal-breaker `miss` = it has it; both `unknown` when the advert has no feature list. The file's facts are the card's own (price now, the file's suburb / type / beds / baths / garages / sizes, the most parking on its adverts).
Tests: `tests/Feature/MarketIntelligence/BuyerFitTest.php` (5).
