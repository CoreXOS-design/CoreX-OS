### H1 — HIGH — DR2 "Add to deal" on an EXISTING deal can never post a property id (the form is dead)
- **Where:** `resources/views/dr2/create.blade.php:249` (`<select id="dr2mp_picker" class="…">` — no `name`, no `form` attribute); `:897-899` (the real standalone form `dr2mp_add_form_real` contains only `@csrf`); `:483`, `:487`, `:489` (the only inputs bound to that form are `allocated_price`, `allocated_commission`, and the submit button); `app/Http/Controllers/Dr2/DealRegisterController.php:1618` (`'property_id' => ['required', …]`).
- **Root cause:** commit `2b950f2ed` correctly replaced the old hidden `dr2mp_add_property_id` input with `<select id="dr2mp_picker" name="property_id" form="dr2mp_add_form_real">`. Commit `3cb1266dd` ("relocate Financials") re-emitted the select WITHOUT `name`/`form` and re-emitted the price/commission box elsewhere, and nothing (no JS, no hidden input — `dr2mpAddFormReal` is referenced only at `:1825-1828` to reformat the commission figure) re-binds the chosen property id to the form.
- **Failure scenario:** open any saved deal → Properties → pick a second eligible property from "Add another property" → enter selling price + commission → click "Add to deal". The POST carries `_token`, `allocated_price`, `allocated_commission` only; `addProperty()` validation fails with "The property id field is required." every time. Multi-property deals can only be created at create-time (`applyCreateTimeMultiProperty`), never extended afterwards.
- **Why tests are green:** `tests/Feature/Dr2/DealAddRemovePropertyControllerTest.php:117,138,160,194,219` post `property_id` straight to the route; `DealMultiPropertyBladeTest` asserts labels only, never the form's field binding.
- **Side note on the 2026-09-13 collision audit:** the `old('property_id')` collision between the deal's own hidden field (`:174`, `:182`) and the add form is now moot only because the add form no longer posts `property_id` at all — i.e. the audit item was "fixed" by breaking the feature, not by renaming the field. Once H1 is fixed by re-adding `name="property_id"` the collision returns unless the add-form field is named differently (e.g. `add_property_id`) and `addProperty()` validates that key.
- **Status:** CONFIRMED (by reading; no runtime needed — the form literally has no such input).

- **Where:** `app/Http/Controllers/CoreX/ContactMatchController.php:225-235` — own scope is `where('created_by_user_id', auth()->id())`, branch scope is `whereHas('createdBy', …)`, and the manager agent filter is `where('created_by_user_id', $agentId)`. `ContactMatch::reassignTo()` (`app/Models/ContactMatch.php:325-353`) moves only `agent_id`. ### M4 — MEDIUM — Public share link: opening the page writes more than a link-open, and the token path reaches two unguarded mutating endpoints
- **Public route inventory:** `GET /shared/match/{token}` (`throttle:30,1`), `GET …/view/{property}` (`throttle:30,1`), `POST …/feedback/{property}` (`throttle:30,1`), `POST …/reengage` (`throttle:reengage-shared-link`) — `routes/web.php:189-194`, no auth by design.
- **Token:** `ContactMatchShare::mint()` uses `Str::ulid()` — 48-bit time prefix + 80 random bits; lookup is DB equality on a `UNIQUE` column (`SharedMatchController::resolveMatch():511-514`), never by id. Adequate; LOW note that ULIDs minted in the same millisecond are sequential (Symfony increments the random part), which is not a practical guessing vector at 80 bits.
- **What a recipient sees:** `MatchingService::propertiesForMatch():304-305` hard-filters `where('agency_id', $match->agency_id)` independently of `AgencyScope` (which is skipped with no auth user, `AgencyScope.php:56-59`), and `resolveDisplayAgent()` guards the `?agent=` override by agency. No cross-agency stock leak found.
- **Mutation beyond logging the open (new in this promotion):** `SharedMatchController::buildMatchGroups():416-419` → `CoreMatchReasonClassifier::classify():80` → `AgencyContactSettings::forAgency()` → `firstOrCreate`. An unauthenticated GET can INSERT the agency's `agency_contact_settings` row (with defaults). Harmless in content, but it is a write triggered by a public URL and it runs on every wishlist section of every open.

- **Status:** CONFIRMED (both). The feedback/recordView shape predates this promotion; the share-token reachability and the settings insert are new.

### M5 — MEDIUM — A share row (and therefore a live public token) is minted on every render of the match-results page
- **Where:** `resources/views/corex/contacts/_match-action-bar.blade.php:57` runs `ContactMatchShare::mint()` inside a Blade `@php` block whenever `$showShareActions` is true (i.e. on every GET of `corex/contacts/{contact}/matches/{match}` — `match-results.blade.php:90`).
- **Consequence:** a DB write on a read; one unconfirmed `contact_match_shares` row per page view, each carrying a token that `SharedMatchController::resolveMatch()` deliberately resolves ("a pending share token intentionally still resolves"). No expiry, no cleanup, no cap. Every reload/back-button/refresh grows the table and mints another resolvable public URL that was never sent to anyone. The share log and `lastSharedAt()` are correctly filtered on `confirmed_at`, so history is not polluted — only the table and the token space are.
- **Status:** CONFIRMED (design; spec calls it "harmless", but it is an unbounded write-on-read of public credentials).
