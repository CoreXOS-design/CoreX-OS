What was ours to decide: **(1) Storage naming.** The brief suggested `listing_id` / `date` / `count`; CoreX calls a listing a `property` everywhere (`property_portal_metrics.property_id`) and `count` is an awkward MySQL column, so storage is `property_id` / `stat_date` / `metric_count`. Internal shape is not the contract; the HTTP surface is byte-identical to spec. **(2) `days[]` vs `delta`.** They are redundant by the website's own construction (delta == sum of days), so consuming both would double every number. `days[]` wins — it is the time series, and daily granularity is what makes charts and arbitrary date ranges possible; `delta` is used ONLY when an entry carries no usable `days[]`, attributed to `generated_at`'s date. `totals` is never added, only stored — it is the drift check against our own SUM, and it is what the panel shows as "all time" so a lost batch can't silently shrink the headline figure. **(3) `listings: max:1000` in validation, not 200.** The contract says up to 200 per request, but a 422 on 201 entries would strand a batch the website can only ever resend unchanged — the cap is a payload-size backstop, not a contract check. Ingest runs in one transaction so a 2xx is only ever returned for a batch that is durably stored, which is exactly what that watermark trusts. Idempotency is enforced by a **database unique key**, not a read-then-write, so two concurrent retries of the same `batch_id` cannot both apply — the loser catches `UniqueConstraintViolationException` and answers from the stored row. Metric keys are stored on a **safety floor** (`^[a-z0-9_]{1,40}$`), not a whitelist: a new metric the website starts sending lands with no CoreX deploy, and a key that can't be stored is dropped alone rather than failing the listing or the batch.
